🏗 План рефакторинга: Переход от MVP к Scalable App
1. Уровень API (Backend)
Проблема: Синхронный http.server блокирует весь поток при каждом запросе.

Замена фреймворка: Перейти на FastAPI (или Flask). Это даст асинхронность (async/await), автоматическую документацию API (Swagger) и нормальную обработку ошибок.

Разделение ответственности:

main.py — только запуск сервера.

routes.py — описание эндпоинтов.

services.py — логика расчетов и запросы к Frankfurter API.

2. Уровень базы данных (Data Layer)
Проблема: Ручное управление sqlite3 через сырые SQL-запросы.

Внедрение ORM: Использовать SQLAlchemy или SQLModel. Это избавит от написания SQL руками и упростит работу с объектами.

Миграции: Вместо самописного migrate.py внедрить Alembic. Это индустриальный стандарт для версионирования схемы БД.

3. Уровень инфраструктуры (Docker & DevOps)
Проблема: Монолитный контейнер (статика + API + БД в одном флаконе).

Docker Compose: Разбить систему на два сервиса:

app: Бэкенд на Python.

nginx: Профессиональный веб-сервер для раздачи статики (HTML/CSS/JS) и проксирования запросов к API. Это снимет нагрузку с Python-сервера.

Environment Variables: Вынести все настройки (порты, URL API, путь к БД) в файл .env.

4. Уровень фронтенда (Frontend Modernization)
Проблема: Логика раздута в одном JS-файле, смешивая UI и расчеты.

Модульность: Разбить JS на модули (ES6 Modules): api.js для запросов, ui.js для рендера, storage.js для работы с LocalStorage.

Error Handling: Добавить визуальные уведомления (Toast), если бэкенд или Frankfurter API недоступны.

5. Новые фичи (Backlog)
Исторические графики: Сохранять курсы каждый час в БД и рисовать график изменения валюты (используя Chart.js).

Healthcheck: Добавить эндпоинт /health, чтобы Docker понимал, что контейнер не просто "жив", а реально работает.
